# S1 runbook — M3 full validation (shared maze, real run)

**Goal:** prove both peers build the *identical* maze from the shared seed in a **real run** (rat-select
→ start, not `open Maze_LVL`), with the client's generation gated on the host's `MazeSeed` and a
fingerprint over the **actually spawned** room actors exchanged host↔client (`MAZE MATCH`).

**Deliverables in this session:**
- `mod/CyberRatsCoop/Game/MazeModule.hpp` / `MazeModule.cpp` — self-contained seed-sync + validation
  module (S1). It supersedes the inline maze logic in `dllmain.cpp` (`onMazeGenBegin`,
  `logMazeFingerprint`, the `m_netSeed`/`m_haveNetSeed` plumbing, the inline `MazeSeed` send/dispatch).
- This runbook.
- `dllmain.cpp` wiring snippet below — applied as the **serial integration step** (not by this session).

`Protocol.h` and `dllmain.cpp` are NOT edited by the module session itself. No new wire messages —
`MazeSeed` (0x10) and `MazeReady` (0x11) are already defined.

## A. `dllmain.cpp` wiring (apply at integration)

The module shares `dllmain`'s existing `std::mutex m_mtx` (single lock order — module critical
sections never nest with `dllmain`'s, so no deadlock). `&m_peerReady` is read-only in the module.

### A.1 include + member

Add near the other includes (after `#include "Net/Protocol.h"`):
```cpp
#include "Game/MazeModule.hpp"
```
Add a member alongside the other game-state members (e.g. after `U::UObject* m_puppet = nullptr;`):
```cpp
crc::MazeModule m_maze;
```

### A.2 bind/configure/init — in `on_unreal_init()`

After the transport + role + `m_forceSeed` are set up and **after** the `RegisterProcessEventPreCallback`
registration (anywhere after `m_playerId` and `m_forceSeed` exist):
```cpp
m_maze.bind(m_transport.get(), m_role, m_playerId, &m_peerReady, &m_mtx);
m_maze.configure(m_forceSeed, /*regenOnLateSeed=*/ m_role == crc::Role::Client);
m_maze.on_unreal_init();
```
> `m_transport` is a `std::unique_ptr<crc::UdpTransport>` → pass `m_transport.get()` (an
> `INetTransport*`). `m_mtx` is passed by address.

### A.3 game thread — in `onProcessEvent(ctx, fn, parms)`

Add ONE line near the top, right after the `if (!ctx || !fn) return;` guard:
```cpp
m_maze.on_process_event(ctx, fn);
```
Then **REMOVE the now-duplicated inline maze logic** from `dllmain` (the module owns it):
- the `m_mazeGenClass` lazy-resolve + `m_mazeGenBeginFn` caching block,
- `if (fn == m_mazeGenBeginFn) { onMazeGenBegin(); return; }`,
- the maze-frame counter `if (m_mazeGenSeen && !m_fpLogged && ++m_mazeGenFrames > 120) { logMazeFingerprint(); ... }`,
- the `onMazeGenBegin()` and `logMazeFingerprint()` member functions,
- members `m_mazeGenClass, m_mazeGenBeginFn, m_mazeGenSeen, m_fpLogged, m_mazeGenFrames, m_netSeed, m_haveNetSeed`.

**Keep** the M2 LabRat local-pawn / puppet logic (the `m_ratTickFn` path, `maintainPuppet`,
`m_labRatClass`) untouched — the module has its **own** `m_labRatClass` / `m_ratTickFn` caches and does
not interfere.

> The global ProcessEvent pre-hook fires for every UFunction call; calling `m_maze.on_process_event`
> first and then `dllmain`'s own `m_ratTickFn` path is fine — both pointer-compare against their own
> cached `UFunction*` and ignore everything else.

### A.4 loop thread — in `on_update()`

After the receive loop (where inbound packets are dispatched) and alongside the PlayerState send,
add:
```cpp
m_maze.on_net_tick();
```

### A.5 inbound dispatch — in `dispatch(fr)`

Route `MazeSeed` + `MazeReady` to the module, and **REMOVE** the existing inline
`case Msg::MazeSeed:` body (the module owns it now):
```cpp
case crc::Msg::MazeSeed:
case crc::Msg::MazeReady:
    m_maze.on_message(fr);
    break;
```

Already done — `mod/CyberRatsCoop/xmake.lua` `add_files(...)` includes `"Game/MazeModule.cpp"`:

### A.7 coop.ini (optional)

The module reads no INI directly; `dllmain` forwards two values via `configure()`:
- `[maze] force_seed = -1` — already read by `dllmain` into `m_forceSeed` (≥0 forces a fixed seed for
  testing on BOTH peers; -1 = use the host's game-rolled / net seed). For a genuine real-run
  validation, leave it **-1** so the host broadcasts the value the menu actually rolled.
- `regenOnLateSeed` is derived in `dllmain` (`= (role == Client)`); no INI key required. To disable
  the client console-reload safety net during testing, pass `false` in A.2.

## C. Two-instance in-game test (real run)

Reuse the established 2-instance method (docs/STATUS.md M1). Both instances write the **same**
`UE4SS.log`.

1. **Host** — launch via Steam (`steam://rungameid/3565080`); role from `coop.ini` = `host` (or
   `-CRCoopRole=host`). Log: `[CRCoop] hosting on UDP 7777`.
2. **Client** — launch the **bootstrap** directly with Steam env (`SteamAppId/SteamGameId=3565080`):
   ```powershell
   & "<install>\Cyber Rats.exe" -CRCoopRole=client -CRCoopConnect=127.0.0.1
   ```
   Log: `[CRCoop] connecting to 127.0.0.1:7777`.
3. Wait for the link: both log `co-op link established` (`peer Hello ok` on host, `HelloAck` on client).
4. **Drive a REAL run** (this is the S1 point — do NOT `open Maze_LVL`): on the **host**, go through the
   rat-select / start-game menu so `GameInstance_LabRats_C."Random Seed Roll"` is actually rolled and
   consumed. Then start the run on the **client** the same way (or let it follow). The client's
   `Maze_Generator:ReceiveBeginPlay` is gated by the module:
   - if the host's `MazeSeed` already arrived → the client applies it before generation;
   - if it arrives late → the client logs a WARN and self-heals (regen / level reload) once the seed lands.

## D. Success criteria — exact `UE4SS.log` lines

A passing run shows (interleaved between the two instances in the shared log):

**Host:**
```
[CRMaze] host run start: seed=<N> paramHash=0x........
[CRMaze] sent MazeSeed seed=<N> paramHash=0x........
[CRMaze] room class matched: MazeRunner_Biome_...   (or Master_Maze_Room)
[CRMaze] local fingerprint rooms=<R> hash=0x<H>
[CRMaze] sent MazeReady player=0 hash=0x<H> rooms=<R>
[CRMaze] received MazeReady player=1 hash=0x<H>
[CRMaze] MAZE MATCH hash=0x<H> rooms=<R>
```

**Client:**
```
[CRMaze] received MazeSeed seed=<N> paramHash=0x........
[CRMaze] client forced maze seed = <N>
[CRMaze] room class matched: MazeRunner_Biome_...
[CRMaze] local fingerprint rooms=<R> hash=0x<H>
[CRMaze] sent MazeReady player=1 hash=0x<H> rooms=<R>
[CRMaze] received MazeReady player=0 hash=0x<H>
[CRMaze] MAZE MATCH hash=0x<H> rooms=<R>
```

**PASS** = at least one peer logs `[CRMaze] MAZE MATCH` with `rooms` > 0 and the same `hash` on both
sides. (The base game generates ~21 rooms on a real run, per docs/hooks.md.)

**FAIL signatures and what they mean:**
- `[CRMaze] MAZE MISMATCH local=0x.... peer=0x....` → seeds applied but layouts diverge. Check the two
  `paramHash` values; a `WARN paramHash mismatch` line means difficulty/level/`Selected LabRat ID`
  differed (so the seed alone can't match the maze) — align the run params.
- `[CRMaze] WARN client gen ran BEFORE seed arrived` with NO later match → the late-seed race fired and
  the self-heal path could not regenerate. Confirm a regen entry (see E) or enable the console reload.
- `rooms=0` in the fingerprint → the room-actor class-name heuristic didn't match. Capture the real
  class name (E) and update `classNameLooksLikeRoom` in `MazeModule.cpp`.

### On-screen behavior
With matching seeds both windows show a visually identical maze layout (same room shapes / corridor
topology). A quick visual diff of the two windows corroborates the `MAZE MATCH` log.

## E. Live confirmations (one-line edits in `MazeModule.cpp`, no structural change)

Use the existing `CRToolkit` dump on a real run to confirm and, if needed, correct:
1. **Room-actor class name(s)** — the exact spelling of the spawned room classes
   (`MazeRunner_Biome_*` vs `Master_Maze_Room`). Edit `classNameLooksLikeRoom()` (the
   `rfind(..., 0) == 0` prefix tests) if they differ. The first matched class is logged as
   `room class matched: <name>` — use that to verify.
2. **Run-start / param source** — that `Setup Dungeon Difficulty` fires with the resolved difficulty
   (it feeds `captureParamHash`). If the run difficulty is sourced elsewhere, add that UFunction to the
   cache block in `on_process_event` and read it in `captureParamHash`.
3. **Late-seed regen entry** — whether `Maze_Generator_C` exposes a clean single-entry regen UFunction.
   `tryRegenIfLateSeed()` tries `Generate Maze` / `Generate` / `Build Maze` / `Spawn Start Room` in
   order; if the real name differs, add it to the `candidates[]` list. Otherwise the console-reload
   fallback (`PlayerController::ConsoleCommand "open Maze_LVL"`) handles it (gated by `regenOnLateSeed`).
