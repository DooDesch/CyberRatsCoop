`docs/protocol.md` exactly.

## Engine constraint that shapes the design (load-bearing)

dllmain hooks the **deprecated** global `RegisterProcessEventPreCallback` form. That pre-callback
**cannot cancel/suppress** the original UFunction call. So the module never relies on blocking a
client's local collect. Authority is enforced by a HOST-owned collected-set mirrored to the client
via `PickupStateSync`; the client additionally disables collision on every local cheese
(`SetActorEnableCollision(false)`) so the engine's own collect path does not fire, and detects pickup
intent by proximity instead — sending a request the host validates. Any local divergence self-heals on
the host's next 1 Hz keyframe.

## (a) EXACT dllmain.cpp wiring

Six edits in `mod/CyberRatsCoop/dllmain.cpp`, mirroring how dllmain already drives M2/M3, plus the
xmake line (already applied in this milestone).

### 1. Include (top, after the existing `#include "Net/Protocol.h"`)
```cpp
#include "Game/Pickups.hpp"
```

### 2. Member (private members block, near `m_puppet`)
```cpp
crc::game::PickupsModule m_pickups;
```

### 3. Bind + init — end of `on_unreal_init()`, AFTER `m_role`/`m_transport`/`m_playerId` are set
(order vs. the `RegisterProcessEventPreCallback` line does not matter; the hook only fires later on
the game thread):
```cpp
m_pickups.bind(m_transport.get(), m_role, m_playerId, &m_peerReady, &m_mtx,
               [this]{ return m_localPawn; });
m_pickups.on_unreal_init();
```
> `m_localPawn` is the `U::AActor*` dllmain already caches in `onProcessEvent` (≈L222). The lambda is
> only ever invoked on the game thread (inside `PickupsModule::on_process_event` → `clientProximityScan`),
> so reading `m_localPawn` there is safe.

### 4. Game-thread forward — inside `onProcessEvent(ctx, fn, parms)`. Place it **right after the
cached-fn resolution block** (immediately after the `if (!m_ratTickFn || !m_mazeGenBeginFn) { ... }`
block, ≈L207) and BEFORE dllmain's own `if (fn == m_mazeGenBeginFn)` early-returns:
```cpp
        m_pickups.on_process_event(ctx, fn);   // M4 pickups/objective (game thread)
```
> It must run before dllmain's early-returns: dllmain returns early for non-LabRat / non-local
> contexts, but the pickups module needs to see `Spawn All Cheese`, `Check for Dungeon Complete`, the
> cheese-collect fn and the exit-overlap fn — none of which are LabRat ticks. The module does its own
> cached-pointer gating, so the extra forwarded calls cost only a handful of pointer compares.

### 5. Run-begin notification — inside `onMazeGenBegin()` (dllmain's existing
`Maze_Generator:ReceiveBeginPlay` pre-hook, game thread), as the LAST line, after the seed is
chosen/forced into `Random Seed Roll`:
```cpp
        m_pickups.notify_run_begin((uint64_t)(uint32_t)seed);
```
> Resets per-run pickup/objective state on both peers (drops the id↔actor maps so the next maze
> rebinds cleanly); on the host it also queues a `RunStart`. If the seed wasn't forced (`seed < 0`),
> pass the game-rolled value if available, or simply `0` — only the per-run reset matters for the
> client; the host's `RunStart.seed` is informational.

### 6. Net-thread send — inside `on_update()`, after the PlayerState send block (≈L152):
```cpp
        m_pickups.on_net_tick();
```

### 7. Inbound dispatch — inside `dispatch(const crc::Frame& fr)`, route the six M4 types to the
module. Add before `default:`:
```cpp
        case Msg::PickupCollected:
        case Msg::PickupStateSync:
        case Msg::ObjectiveReached:
        case Msg::RunStart:
        case Msg::RunEnd:
        case Msg::Restart:
            m_pickups.on_message(fr);
            break;
```
> `dispatch` runs on the UE4SS loop thread; `on_message` touches only PODs under `m_mtx`. No UObject
> access there — world mutation happens later on the game thread in `drainInboundToWorld()`.

### xmake.lua (already applied this milestone)
```lua
    add_files("dllmain.cpp", "Transport/UdpTransport.cpp", "Game/MazeModule.cpp", "Game/Pickups.cpp")
```
> xmake does not glob — every new `.cpp` must be listed. `Pickups.hpp`/`MazeModule.hpp` are
> header-only; `add_includedirs(".")` already covers the `Game/...` and `Net/...` includes.

## (c) 2-instance in-game test

Drive a **real run** (rat-select / start-game), not `open Maze_LVL`: a difficulty-0 direct open spawns
0 cheese, so the module is inert (still a valid smoke test — it must log `enumerated 0 cheese pickups`
and otherwise stay silent).

### Launch
- **Host** via Steam (normal launch). Put `-CRCoopRole=host` in its launch options, or set `role=host`
  in `coop.ini`.
- **Client** via the bootstrap exe, second instance:
  ```pwsh
  & "<game>/Cyber Rats.exe" -CRCoopRole=client -CRCoopConnect=127.0.0.1
  ```
  Or the helper that starts both with isolated `-UserDir` so the two `UE4SS.log`s don't collide:
  ```pwsh
  pwsh scripts/run_two_instances.ps1            # -Dev for the Development exe (richer logs)
  ```

### First-run discovery step (one-time — resolve the unknown UFunction / class names)
`docs/hooks.md` has NOT yet dumped the cheese-collect fn name, the exit class path, or the cheese
class path (difficulty-0 open = 0 instances). On the first real run:
1. Confirm the class paths in `resolveClassesAndFns()` actually resolve. The module currently tries
   `/Game/Pickups/Chese_Pickup.Chese_Pickup_C`, `/Game/Pickups/Last_Chese_Pickup.Last_Chese_Pickup_C`,
   `/Game/Pickups/BP_EnterExit.BP_EnterExit_C`. If `enumerated 0 cheese pickups` prints while cheese
   are clearly present, the paths are wrong — dump the real `/Game/...` paths with CRToolkit
   (`StaticFindObject` / `ForEachUObject`, the same way M0 dumped the others) and update those three
   `StaticFindObject<UClass*>` calls. (The `FindAllOf(STR("Chese_Pickup_C"), ...)` enumeration keys on
   the short class name and is path-independent; only the `IsA`/last-cheese discrimination needs the
   class objects.)
2. Watch for `[CRCoop] M4: cheese collect fn resolved = <Name>`. The module probes a candidate list
   (`On Collected`, `Collect`, `Collected`, `Pickup`, `On Pickup`, `Interact`, `On Interact`) on
   `Chese_Pickup_C`. If none match, the line never prints — host collect still works via the natural
   game path being detected, and the client still works via the proximity fallback, but to make the
   host's `onCheeseCollectHook` fire on the exact collect event, find the real collect fn (likely an
   `Interact_Interface` impl) via `ForEachFunction` on a live `Chese_Pickup_C` and add its name to
   `kCheeseCollectCandidates` in `Pickups.cpp`.
3. The exit hooks `BP_EnterExit_C:ReceiveActorBeginOverlap`. If the exit uses a different trigger,
   dump `BP_EnterExit_C` functions and update the `m_exitOverlapFn` resolution. Only fn-name/class-path
   constants change; the flow is fixed.

### Success criteria — exact `UE4SS.log` lines / on-screen behavior

Check each instance's `UE4SS.log` (host vs. client UserDir if using the helper).

1. **Module up (both):**
   ```
   [CRCoop] M4 pickups module ready (role=1)      # host  (Role::Host == 1)
   [CRCoop] M4 pickups module ready (role=2)      # client(Role::Client == 2)
   ```
2. **Run begin (both, from dllmain's gen-begin hook):**
   ```
   [CRCoop] M4: run begin (runId=<R>, seed=<S>)
   ```
3. **Cheese set built (both, a few frames after Spawn All Cheese):**
   ```
   [CRCoop] M4: Spawn All Cheese seen; deferring enumeration
   [CRCoop] M4: enumerated <N> cheese pickups (role=...)
   ```
   `<N>` MUST be identical on host and client (same maze ⇒ same cheese ⇒ same ids).
4. **Host pushes the keyframe; client mirrors it.** No explicit client log for the keyframe receipt,
   but the client's `m_pickupState` is now seeded — proven by step 6.
5. **Collect on the HOST:** host's rat walks onto a cheese (natural collect path).
   - Host log:   `[CRCoop] M4: host collected cheese id=0x<ID> kind=<0|1>`
   - Client log: `[CRCoop] M4: applied collected cheese id=0x<ID>`
   - On-screen: that cheese **disappears on BOTH** machines.
6. **Collect on the CLIENT:** client's rat walks within ~1.5 m of a still-present cheese.
   - Client log: `[CRCoop] M4: client request collect id=0x<ID> kind=<0|1>`
   - Host log:   `[CRCoop] M4: host confirmed client collect id=0x<ID>`
   - Client log: `[CRCoop] M4: applied collected cheese id=0x<ID>`
   - On-screen: that cheese **disappears on BOTH** machines; the host's authoritative count increments
     exactly once (no double-count).
7. **Same `<ID>` for the same physical cheese on both machines** — the load-bearing assertion. Eyeball
   that a cheese at a given maze cell logs the same `id=0x....` on host and client.
8. **Objective / exit:** a rat reaches `BP_EnterExit_C`.
   ```
   [CRCoop] M4: exit reached (byPlayer=<0|1>) -> ObjectiveReached      # the reaching peer
   [CRCoop] M4: ObjectiveReached id=0x0001 byPlayer=<0|1>              # the other peer
   ```
9. **Dungeon complete (host-driven):** when the game's own `Check for Dungeon Complete` passes.
   - Host log:   `[CRCoop] M4: dungeon complete -> RunEnd(win) runId=<R>`
   - Client log: `[CRCoop] M4: RunEnd runId=<R> result=1 reason=0`
   A **single shared** run-complete event.

### Negative / edge checks
- **Double-collect race:** both rats touch the same cheese ~simultaneously. Only the host's state
  decides; the loser's request is answered with the current (collected) state — client reconciles, no
  double count. Expect one `host confirmed`/`host collected` and the cheese gone on both.
- **Packet loss / late state:** the host's 1 Hz `PickupStateSync` keyframe re-converges a client that
  missed a reliable delta. `applied collected` is idempotent. To test: artificially drop a confirm and
  confirm the client still hides the cheese within ~1 s.
- **0-cheese (difficulty-0 open):** `enumerated 0 cheese pickups` then silence. Module inert. PASS.

## Design notes (for the integrator / reviewer)

- **Stable ids by maze cell:** `id = hash16(cellX, cellY, slot)` (`Pickups.hpp::hash16`), cell =
  `lround(worldPos / kCell)` with `kCell = 100 cm`; the Z cell is folded into the Y mix and `slot=1`
  for `Last_Chese_Pickup_C` else 0. Both peers sort pickups by quantized cell before id assignment so
  any hash-collision perturbation (`id ^= 0x9E37`) is identical on both — that is what lets the same
  physical cheese get the same id WITHOUT exchanging a per-pointer map. If a real run shows id drift,
  raise `kCell` (coarser quantization) in `Pickups.cpp`.
- **Authority model:** host owns the authoritative `m_pickupState` (`0` present / `1` collected) and
  the count; it validates every collect (its own natural collect, or a client `PickupCollected`
  request) and broadcasts a `PickupStateSync` delta (the delta IS the client's confirm), plus a 1 Hz
  full keyframe. Client mirror-only; it disables collision on local cheese and proposes via proximity.
- **Run lifecycle:** `RunStart` (host, on gen-begin), `RunEnd` (host, on dungeon-complete or
  objective), `Restart` (host) all on the reliable control channel. `ObjectiveReached` is bidirectional
  (client proposes, host re-broadcasts).
- **Threading:** UObject access ONLY in `on_process_event`/`notify_run_begin` (game thread).
  `on_net_tick`/`on_message` touch PODs under the shared `m_mtx`. No `AActor*`/`UObject*` ever crosses
  the mutex — only `uint16_t` ids and small PODs. The mutex is never held across a UObject call
  (`drainInboundToWorld` copies the id list out under lock, releases, then mutates actors).
