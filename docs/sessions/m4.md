# M4 — Pickups & Objective (host-authoritative) — integration + test runbook

Module: `mod/CyberRatsCoop/Game/Pickups.{hpp,cpp}`, struct `crc::game::PickupsModule`.
Depends on: M1 transport, M2 player presence, M3 shared-maze seed-sync (all done & verified).

This module is self-contained (no `CoopCtx`). It reuses dllmain's transport, role, playerId,
`m_peerReady`, and **the same `m_mtx`**, all handed in via `bind()`. It defines the M4 wire structs
locally (the `Msg` enum values exist in `Net/Protocol.h`, but the typed structs do not, and we must
not edit `Protocol.h` — promote them later).

---

## (a) EXACT dllmain.cpp wiring

All five edits are in `mod/CyberRatsCoop/dllmain.cpp`. They mirror how dllmain already drives M2/M3.

### 1. Include (top, after the existing `#include "Net/Protocol.h"`)
```cpp
#include "Game/Pickups.hpp"
```

### 2. Member (in the private members block, near `m_puppet`)
```cpp
crc::game::PickupsModule m_pickups;
```

### 3. Bind + init (end of `on_unreal_init()`, AFTER `m_role`/`m_transport`/`m_playerId` are set,
and after the `RegisterProcessEventPreCallback` line — order vs. the hook does not matter, the hook
only fires later on the game thread)
```cpp
m_pickups.bind(m_transport.get(), m_role, m_playerId, &m_peerReady, &m_mtx,
               [this]{ return m_localPawn; });
m_pickups.on_unreal_init();
```
> `m_localPawn` is the `U::AActor*` dllmain already caches in `onProcessEvent` (L222). The lambda is
> only ever invoked on the game thread (inside `PickupsModule::on_process_event`), so reading
> `m_localPawn` there is safe.

### 4. Game-thread forward (inside `onProcessEvent(ctx, fn, parms)`). It MUST run on EVERY hook
call — NOT as the last line of the method (that point sits after dllmain's `isLocal`/non-LabRat
early-returns, so the module would never see the non-LabRat UFunctions it needs). Put it **right
after the cached-fn resolution block**, i.e. immediately after line 207 (`if (!m_ratTickFn ...) ... }`)
and BEFORE `if (fn == m_mazeGenBeginFn)` on line 209:
```cpp
        m_pickups.on_process_event(ctx, fn);   // M4 pickups/objective (game thread)
```
> Putting it before dllmain's own early-returns is required: dllmain returns early for non-LabRat /
> non-local contexts, but the pickups module needs to see `Spawn All Cheese`,
> `Check for Dungeon Complete`, the cheese-collect fn, and the exit-overlap fn — none of which are
> LabRat ticks. The module does its own pointer-compare gating, so the extra calls are cheap.

### 5. Run-begin hook (inside `onMazeGenBegin()`, the existing `Maze_Generator:ReceiveBeginPlay`
pre-hook — game thread). Add as the LAST line of the method, after the seed has been chosen/forced
(after the `if (m_role == crc::Role::Host && m_peerReady) { ... }` block, ~L288). This is what resets
per-run pickup state on both peers and queues the host's `RunStart`. `seed` is the value dllmain just
resolved (`m_netSeed` on the client, else `m_forceSeed`); pass whatever non-negative seed was used,
or `0` if the seed was not forced:
```cpp
        m_pickups.notify_run_begin(seed >= 0 ? (uint64_t)(uint32_t)seed : 0);
```
> Without this call, RunStart is never emitted and pickup state never resets between runs. It runs on
> the game thread (inside the pre-hook), which is correct — `notify_run_begin` only touches PODs under
> `m_mtx` plus the game-thread-only id↔actor maps it clears.

### 6. Net-thread send (inside `on_update()`, after the PlayerState send block, ~L152)
```cpp
        m_pickups.on_net_tick();
```

### 7. Inbound dispatch (inside `dispatch(const crc::Frame& fr)`, in the `switch`, route the six M4
types to the module). Add these cases before `default:`:
```cpp
        case Msg::PickupCollected:
        case Msg::PickupStateSync:
        case Msg::ObjectiveReached:
        case Msg::RunStart:
        case Msg::RunEnd:
        case Msg::Restart:
            m_pickups.on_message(fr);
            break;
```
> `dispatch` runs on the UE4SS loop thread; `on_message` touches only PODs under `m_mtx`. No UObject
> access. World mutation happens later on the game thread in `drainInboundToWorld()`.

### xmake.lua
Add `Game/Pickups.cpp` to the `add_files(...)` line, KEEPING the existing entries (notably
`Game/MazeModule.cpp` from S1 — do not drop it). The full line is:
```lua
    add_files("dllmain.cpp", "Transport/UdpTransport.cpp", "Game/MazeModule.cpp", "Game/Pickups.cpp")
```
(`Pickups.hpp` is header-only and needs no entry. `add_includedirs(".")` already covers
`Game/...` and `Net/...` includes.) This matches the current `mod/CyberRatsCoop/xmake.lua`.

### Coordination with MazeModule (S1/M3)
`MazeModule` also pre-hooks `Maze_Generator:ReceiveBeginPlay` and forwards `on_process_event`. Both
modules do their own cached-pointer gating, so calling both forwards every hook call is safe and
cheap. Call `m_pickups.notify_run_begin(seed)` exactly ONCE per run from the canonical begin-play
handler (dllmain's `onMazeGenBegin()` in the current tree). If S1's MazeModule later subsumes
`onMazeGenBegin`, move the `notify_run_begin` call into `MazeModule`'s begin-play handler instead and
keep it single-fire.

## (c) 2-instance in-game test

Drive a **real run** (rat-select / start-game), not `open Maze_LVL` — a difficulty-0 direct open
spawns 0 cheese, so the module is inert (this is itself a valid smoke test: it must log
`enumerated 0 cheese pickups` and do nothing else).

### Launch
- **Host** via Steam (normal launch). Confirm `-CRCoopRole=host` is in its launch options, or set
  `role=host` in `coop.ini`.
- **Client** via bootstrap, second instance:
  ```pwsh
  & "<game>/Cyber Rats.exe" -CRCoopRole=client -CRCoopConnect=127.0.0.1
  ```
  Or use the helper which starts both with isolated `-UserDir`:
  ```pwsh
  pwsh scripts/run_two_instances.ps1            # add -Dev for the Development exe (richer logs)
  ```

### First-run discovery step (one-time — resolve the unknown UFunction names)
`docs/hooks.md` has NOT yet dumped the exact cheese-collect fn or the exit-overlap signature
(difficulty-0 open = 0 cheese). In the first real run, dump them:
1. With the run loaded and cheese present, watch `UE4SS.log` for
   `[CRCoop] M4: cheese collect fn resolved = <Name>`. The module probes a candidate list
   (`On Collected`, `Collect`, `Collected`, `Pickup`, `On Pickup`, `Interact`, `On Interact`) on
   `Chese_Pickup_C`. If none match, the line never prints — then use CRToolkit /
   `ForEachFunction` on a live `Chese_Pickup_C` instance to find the real collect fn (likely an
   `Interact_Interface` impl) and add its name to `kCheeseCollectCandidates` in `Pickups.cpp`.
2. For the exit, the module hooks `BP_EnterExit_C:ReceiveActorBeginOverlap`. If the exit uses a
   different trigger, dump `BP_EnterExit_C` functions and update `m_exitOverlapFn` resolution in
   `resolveClassesAndFns()`. Only the **fn-name constants** change; the flow is fixed.

### Success criteria — exact `UE4SS.log` lines / on-screen behavior

Look in each instance's `UE4SS.log` (host vs. client UserDir if using the helper).

1. **Module up (both):**
   ```
   [CRCoop] M4 pickups module ready (role=1)      # host
   [CRCoop] M4 pickups module ready (role=2)      # client
   ```
1b. **Run begin (both, when the maze generator's ReceiveBeginPlay fires — requires the step-5
   `notify_run_begin` wiring):**
   ```
   [CRCoop] M4: run begin (runId=<R>, seed=<S>)   # both
   [CRCoop] M4: RunStart runId=<R> countdown=0ms  # CLIENT only (host->client RunStart)
   ```
   If the `run begin` line never appears, the `notify_run_begin` wiring (step 5) is missing.
2. **Cheese set built (both, after Spawn All Cheese):**
   ```
   [CRCoop] M4: Spawn All Cheese seen; deferring enumeration
   [CRCoop] M4: enumerated <N> cheese pickups (role=...)
   ```
   `<N>` MUST be identical on host and client (same maze ⇒ same cheese ⇒ same ids).
3. **Host pushes the keyframe; client mirrors it.** (No explicit client log for the keyframe, but
   the client's `m_pickupState` is now seeded — proven by step 4.)
4. **Collect on the HOST:** host's rat walks onto a cheese.
   - Host log: `[CRCoop] M4: host collected cheese id=0x<ID> kind=<0|1>`
   - Client log: `[CRCoop] M4: applied collected cheese id=0x<ID>`
   - On-screen: that cheese **disappears on BOTH** machines.
5. **Collect on the CLIENT:** client's rat walks onto a (still-present) cheese.
   - Client log: `[CRCoop] M4: client request collect id=0x<ID> kind=<0|1>`
   - Host log:   `[CRCoop] M4: host confirmed client collect id=0x<ID>`
   - Client log: `[CRCoop] M4: applied collected cheese id=0x<ID>`
   - On-screen: that cheese **disappears on BOTH** machines. The host's cheese counter increments
     once (no double-count).
6. **Same `<ID>` for the same physical cheese on both machines** — the load-bearing assertion.
   Eyeball that a cheese at a given maze cell logs the same `id=0x....` on host and client.
7. **Objective / exit:** a rat reaches `BP_EnterExit_C`.
   ```
   [CRCoop] M4: exit reached (byPlayer=<0|1>) -> ObjectiveReached
   [CRCoop] M4: ObjectiveReached id=0x0001 byPlayer=<0|1>   # on the peer
   ```
8. **Dungeon complete (host-driven):** when the game's own `Check for Dungeon Complete` passes.
   - Host log: `[CRCoop] M4: dungeon complete -> RunEnd(win) runId=<R>`
   - Client log: `[CRCoop] M4: RunEnd runId=<R> result=1 reason=0`
   This is a **single shared** run-complete event.

### Negative / edge checks
- **Double-collect race:** both rats touch the same cheese ~simultaneously. Only the host's state
  decides; the loser's request is answered with the current (collected) state — client reconciles,
  no double count. Expect one `host confirmed` (or `host collected`) and the cheese gone on both.
- **Packet loss / late state:** the host's 1 Hz `PickupStateSync` keyframe re-converges a client that
  missed a delta. `applied collected` is idempotent (hide-already-hidden = no-op).
- **0-cheese (difficulty-0 open):** `enumerated 0 cheese pickups` then silence. Module inert. PASS.

## Design notes carried forward (for the integrator)

- **Stable ids by maze cell:** `id = hash16(cellX, cellY, slot)` (header `hash16`), cell =
  `lround(worldPos / 100cm)`, `slot=1` for `Last_Chese_Pickup_C` else 0. Both peers sort pickups by
  quantized cell before id assignment so any hash-collision perturbation is identical on both — this
  is what lets the same physical cheese get the same id WITHOUT exchanging a per-pointer map. If a
  real run shows id drift, raise `kCell` (coarser quantization) in `Pickups.cpp`.
- **Client suppression:** on the client, every enumerated cheese gets `SetActorEnableCollision(false)`
  so the engine's own collect path never fires; the client instead detects intent by proximity
  (`kPickupRadiusSq`, ~1.5 m) and sends a request. Host keeps collision on and uses the natural path.
- **Threading:** UObject access ONLY in `on_process_event` (game thread). `on_net_tick` /
  `on_message` touch PODs under the shared `m_mtx`. No `AActor*`/`UObject*` ever crosses the mutex —
  only `uint16_t` ids and small PODs. The mutex is never held across a UObject call
  (`drainInboundToWorld` copies the id list out under lock, releases, then mutates actors).
